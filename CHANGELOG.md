## 2026-08-08 — RLS на 7 таблицах Supabase + фикс BUG-019 (`api/decks.js` sync 500 на успехе)

**RLS**: включён (без политик — весь доступ через `api/*.js` с `SUPABASE_SERVICE_KEY`, RLS его не касается) на `user_stats`, `referrals`, `events`, `daily_sessions`, `deck_words`, `user_word_progress`, `payments`. Тот же паттерн, что уже стоял у `vocab_items`. Advisor подтвердил: ERROR-линты `rls_disabled_in_public` пропали. Заодно поправлен WARN `function_search_path_mutable` на `update_updated_at`. См. `BACKLOG.md` (пункт закрыт) и обсуждение возможных будущих кейсов прямого клиентского доступа.

**BUG-019** (найден при постфактум-смоуке RLS-изменения, см. `BUGLOG.md`): `api/decks.js`, `action: 'sync'` — `sb()`-хелпер парсил тело ответа Supabase как JSON во всех случаях, кроме `res.status === 204`. Но POST-upsert с `Prefer: resolution=merge-duplicates` (без явного `return=representation`) отвечает `201` с ПУСТЫМ телом — `res.json()` падал с `Unexpected end of JSON input`, эндпоинт возвращал клиенту `500`, хотя сама запись в БД проходила успешно (данные не терялись, ломался только ответ). Пофикшено: `sb()` теперь проверяет по факту наличия тела (`res.text()` → `JSON.parse` только если непусто), а не гадает по конкретному статус-коду. Проверено: build + смоук 200/200 зелёные, живой прогон `action: 'sync'` против прод-БД — `200 {"ok":true,...}` вместо `500`.

## 2026-08-08 — BUG-020: dev-обход подписи Telegram работал и на проде (auth bypass)

Найдено при прод-проверке живым `curl` боевого `/api/sync` (после пуша RLS/BUG-019). `api/sync.js:39` — условие `NODE_ENV === "development" || initData === "dev"` не было ограничено окружением: на проде (`NODE_ENV` там не `"development"`) достаточно было прислать `{"initData":"dev"}`, чтобы полностью обойти HMAC-проверку Telegram и получить `200` как `telegram_id: 0` — без бот-токена, без подписи. Подтверждено живым запросом к `https://alef-betbpt.vercel.app/api/sync`.

Пофикшено: обход теперь требует `process.env.ALLOW_DEV_BYPASS === "1"` (переменная окружения, которая не должна задаваться в Vercel-проде) вместе с `initData === "dev"` — одной строки в теле запроса больше недостаточно. Проверено: build + смоук 200/200; симуляция прод-окружения (флаг не задан) → `403`; симуляция локальной разработки (`ALLOW_DEV_BYPASS=1`) → dev-flow по-прежнему работает, `200`. ⚠️ Осталось вручную: владельцу зайти в Vercel → Environment Variables и убедиться, что `ALLOW_DEV_BYPASS` не задан в Production (пункт в `BACKLOG.md`, у ассистента нет доступа к Vercel без авторизации).
